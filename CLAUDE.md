# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Django backend for FACT (Filipino Americans Coordinating Together), an annual UIUC conference. Handles delegate/facilitator registration, workshop selection and capacity, Eventbrite payment verification, UIUC Shibboleth SSO, and admin tooling (bulk data upload, notifications, agenda). Deploys to DigitalOcean App Platform; the frontend is a separate repo (`fact-2026-frontend`) on Vercel.

## Commands

Use the system `python` on PATH, not `.venv` — the checked-in `.venv` has no packages installed and is effectively dead; `pip install -r requirements.txt` and everything else should target the system interpreter. Any Python 3.10+ works — Django 5.2 (LTS) supports 3.10 through 3.14.

```bash
pip install -r requirements.txt          # install deps
python manage.py runserver               # dev server at :8000
python manage.py test                    # full suite
python manage.py test registration.payment.tests -v 2          # one module, verbose
python manage.py test registration.payment.tests.VerifyPaymentPOSTTest.test_general_paid_order_succeeds  # one test
python manage.py makemigrations registration   # after model changes
python manage.py migrate
```

No linter/formatter is configured in this repo.

`.env` (gitignored) controls local dev: `DEVELOPMENT_MODE=True` switches the DB to SQLite, and is also the default for `SAML_MOCK_MODE` and `EVENTBRITE_MOCK_MODE` (see below) and for the email backend. Without it, the app expects `DATABASE_URL` (Postgres) and will raise on startup if missing.

## Architecture

**Django 5.2 (LTS)** — upgraded from 4.2.15 in 2026-08 specifically to pick up Python 3.14 support (4.2 tops out at 3.12; on 3.14 it crashes in Django's own debug-error-page rendering, `Context.__copy__`, on any 5xx test response — unrelated to application code, but made the test suite unreliable on newer Python). The upgrade needed no code changes — nothing in this codebase used a since-removed 4.2 API. `settings.py`'s header comment saying "Generated by... Django 5.0" now roughly matches reality.

**Apps:**
- `registration` — the core app. Not further split into Django apps; instead each feature area is a subfolder with its own `views.py` + `tests.py` (`delegate/`, `workshop/`, `location/`, `school/`, `facilitator/`, `payment/`), all wired together in `registration/urls.py`. Follow this pattern for new registration-related endpoints rather than creating a new Django app.
- `fact_admin` — admin-only endpoints (notifications, agenda, bulk actions, data export), same subfolder-per-feature convention.
- `one_time_verification` — email OTP for non-UIUC students.
- `shibboleth_auth` — UIUC Shibboleth SAML SSO (`/saml/login/`, `/saml/acs/`, `/saml/metadata/`, `/saml/status/`).

**View style:** plain function-based views returning `JsonResponse`, no Django REST Framework anywhere in the codebase. New endpoints should match this, not introduce DRF serializers/viewsets.

**Local mock-mode pattern:** three independent settings all default to `DEVELOPMENT_MODE` and let the app run fully locally without real external credentials:
- `SAML_MOCK_MODE` — skips the real UIUC IDP, auto-logs in a fake `testuser@illinois.edu` (`shibboleth_auth/views.py`).
- `EVENTBRITE_MOCK_MODE` — skips the real Eventbrite API. `registration/payment/eventbrite_client.py` encodes fake orders as `MOCK_ORDER_<ticket_type>_<discount_code_or_none>`, with an optional `PENDING_` prefix to simulate an incomplete order.
- Email backend switches to file-based (writes to `test_emails/`) instead of real Gmail SMTP whenever `DEVELOPMENT_MODE` is on or tests are running — real SMTP only fires in an actual deployed environment.

New integrations with external services should follow this same pattern (a mock branch gated on a dedicated `*_MOCK_MODE` setting defaulting to `DEVELOPMENT_MODE`) rather than requiring real credentials for local dev.

**Auth model:** three separate, non-overlapping login systems, each with its own session-based auth and URL namespace — delegates (`registration/delegate/`, plus Shibboleth auto-provisioning via `shibboleth_auth`), facilitators (`registration/facilitator/`), and admins (`fact_admin/login/`). A `Delegate`/`Facilitator` is a `OneToOneField` profile hanging off Django's built-in `User`.

**Payment verification:** `Delegate.payment_status`/`ticket_type`/`eventbrite_order_id` (set in `registration/models.py`) gate workshop registration. Two separate endpoints can create `Registration` rows — `POST /registration/delegates/` and `PUT /registration/delegate/me/` — and both carry the same payment guard; if you add a third way to register for workshops, it needs the same check. UIUC students get single-use, tier-scoped Eventbrite discount codes (`UIUCPromoCode` model) issued after Shibboleth verification via `POST /registration/uiuc-promo-code/`; `POST /registration/verify-payment/` is the only place that ever sets `payment_status=paid`, and it always derives `ticket_type` from the Eventbrite order itself, never from client input.

**Testing convention:** plain `django.test.TestCase` + `Client()`, JSON bodies via `content_type="application/json"`. Assert on real DB state (e.g. `Registration.objects.filter(...).exists()`), not just response status codes — a few real bugs in this codebase would only show up that way. `@override_settings(EVENTBRITE_MOCK_MODE=True)` (or `SAML_MOCK_MODE`) on test classes that exercise those integrations; no test should ever call a real external API.

**Deployment:** DigitalOcean App Platform (PaaS, no root access — native C deps like `libxmlsec1-dev` for `python3-saml` go in the root `Aptfile`, not apt-get). `.github/workflows/django.yml` runs the test suite on push/PR to `main`; it does not deploy — deployment is DO App Platform's own GitHub integration watching `main` directly, and it deploys regardless of whether the Actions run passed. CI is a status check, not a deploy gate.

**CI env vars:** GitHub Actions secrets and DO's environment variables are two entirely separate stores — configuring one has no effect on the other. The workflow's `Run Tests` step uses `${{ secrets.X || 'fallback' }}` for every var that's read via `env("NAME")` with no code-level default (`EMAIL_HOST_USER`, `RESET_PASSWORD_URL`, `ACCOUNT_SET_UP_URL`), so real secrets are optional — CI passes with none configured, using obviously-fake placeholders, and picks up a real value automatically if one's ever added. `DEVELOPMENT_MODE` is the only load-bearing one and is set as a plain (non-secret) `"True"` directly in the workflow, since it isn't sensitive. Watch for the empty-string trap if editing this file: an *unconfigured* GitHub secret evaluates to an empty string, not a missing env var, and `django-environ`'s `env("NAME", default=...)` treats present-but-empty as "provided" — it will not fall through to the default.

None of these tests ever hit a real external service regardless of what's configured (`EVENTBRITE_MOCK_MODE`/`SAML_MOCK_MODE` gate that, independent of whether email/URL secrets are real or fake) — that's deliberate, per this repo's own testing convention below, not a gap this fix introduced.

### Config reference: which env vars go where

Every var below is read by the *same name* in every environment — nothing should ever have the same secret *value* copied between local/CI and production, only the name is shared. "Required" means the app breaks or misbehaves without a real value there; everything else either has a safe code default or genuinely doesn't matter in that environment.

| Var | Local `.env` | GitHub CI | DigitalOcean (prod) |
|---|---|---|---|
| `DEVELOPMENT_MODE` | `True` | `"True"` (hardcoded in the workflow, not a secret) | `False` / unset |
| `DJANGO_SECRET_KEY` | any string | optional (falls back to a generated key if unset) | **required** — real, unique, freshly generated (`python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"`) — never reuse a value that's been pasted anywhere outside its own env store |
| `DJANGO_ALLOWED_HOSTS` | not needed (code default: `127.0.0.1,localhost`) | not needed | your real domain(s), e.g. `fact.psauiuc.org` — bare hostnames only, no scheme (`http://...` here does nothing, silently ignored) |
| `CORS_ALLOWED_ORIGINS` | not needed | not needed | usually not needed either — code default already includes `localhost:3000`, `127.0.0.1:3000`, `https://psauiuc.org`, `https://fact.psauiuc.org` |
| `EMAIL_HOST_USER` / `EMAIL_HOST_PASSWORD` | fake placeholders, unused (file email backend always used locally/under test) | optional, doesn't affect test outcome either way | **required** — real Gmail address + a Gmail **App Password** (not the account's login password — Gmail requires this for SMTP) |
| `RESET_PASSWORD_URL` / `ACCOUNT_SET_UP_URL` | `http://localhost:3000/my-fact/reset-password` / `http://localhost:3000/facilitators/account-set-up` (paths confirmed to match `fact-frontend-2026`'s actual `[slug]` routes) | optional placeholders (already set in the workflow) | **required** — same paths, real frontend domain |
| `EVENTBRITE_MOCK_MODE` | `True` (default, follows `DEVELOPMENT_MODE`) | not needed (tests `@override_settings` this per-class) | `False` once a real Eventbrite token/org/event ID are in hand |
| `EVENTBRITE_API_TOKEN` / `EVENTBRITE_EVENT_ID` / `EVENTBRITE_ORGANIZATION_ID` / `EVENTBRITE_TICKET_CLASS_*` | not needed while mocked | not needed | **required** once `EVENTBRITE_MOCK_MODE=False` — still not obtained as of this writing, see `docs/action_items.md` |
| `SAML_MOCK_MODE` | `True` (default, follows `DEVELOPMENT_MODE`) | not needed (tests `@override_settings` this per-class) | `False` once UIUC approves the SP registration (see below) |
| `SAML_SP_BASE_URL` | not needed (default `http://localhost:8000`) | not needed | **required** — `https://fact.psauiuc.org` (or wherever this deploys); the SP cert's CN and the metadata's ACS URL both derive from this |
| `SAML_SP_ENTITY_ID`, `SAML_SP_CERT_FILE`, `SAML_SP_KEY_FILE` | not needed (real UIUC-shaped defaults already in `settings.py`) | not needed | needed once real SAML is live — see the cert-deployment gap below before relying on the file-path defaults |
| `SAML_IDP_ENTITY_ID`, `SAML_IDP_SSO_URL`, `SAML_IDP_SLO_URL`, `SAML_IDP_CERT` | not needed (defaults are UIUC's real, public IDP values already) | not needed | same defaults work in prod too — these don't change per-SP, only your own SP side does |
| `SAML_MOCK_TARGETED_ID` / `SAML_MOCK_AFFILIATION` | optional (has a working default) | not needed | dead once `SAML_MOCK_MODE=False` — only read when mocking |

### UIUC Shibboleth SP registration — where this actually stands

All four SAML endpoints exist and work in mock mode: `saml_login`, `saml_acs`, `saml_metadata`, `saml_status` (`shibboleth_auth/views.py`, mounted at `/saml/` in `fact_registration_backend/urls.py`). The self-signed SP cert/key already exist locally (`saml/generate_certs.sh`, 20-year validity, correctly gitignored — never commit `sp-key.pem`).

**What actually goes to UIUC:** only the metadata XML that `GET /saml/metadata/` serves (it embeds the SP cert's *public* half automatically via python3-saml's `get_sp_metadata()`). **Never send `sp-key.pem` anywhere** — `shibboleth_auth/saml_config.py` only ever reads it server-side to sign outgoing requests; it has no code path that transmits it. State explicitly in the registration what's being requested: only `eduPersonTargetedID` + `eduPersonAffiliation`, nothing identity-revealing (name/email/NetID) — matches what `saml_acs` actually parses.

**Known gap, unresolved:** `SAML_SP_CERT_FILE`/`SAML_SP_KEY_FILE` are read from disk (`open(cert_file)`/`open(key_file)` in `saml_config.py`). Since those `.pem` files are gitignored (correctly — a private key must never be committed), a DigitalOcean deploy pulling from GitHub won't have them either, and nothing currently puts them there. Needs a fix (e.g. read PEM content directly from a DO env var instead of a file path) before real Shibboleth can work in a deployed environment — not yet done.

**Actual next steps, in order:** (1) regenerate the SP cert for the real hostname — `./saml/generate_certs.sh fact.psauiuc.org`, not `localhost`; (2) solve the cert-file deployment gap above; (3) deploy for real (via DO's actual gunicorn-based run command — **not** `manage.py runserver`, which is dev-only and never what runs in production); (4) hit the live `https://fact.psauiuc.org/saml/metadata/` to get the real metadata XML; (5) submit that XML to UIUC's iTrust Federation Registry (`go.illinois.edu/itrust`, per `generate_certs.sh`'s own printed next-step) along with the attribute/purpose info above; (6) once approved, flip `SAML_MOCK_MODE=False` in DO.
